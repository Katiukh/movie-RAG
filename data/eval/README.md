# Retrieval gold benchmark v1

Корпус: `data/processed/movies.jsonl`, 500 документов. Document ID — существующий
`url` VK-поста, тот же ключ, по которому Hybrid объединяет выдачи. Один фильм-пост
равен одному документу; название не является ID. Индексируемые поля:
`title + what + about + why`. `not_for`, год и дата не служат основаниями разметки.

`retrieval_eval_candidates.jsonl` — 50 авторских кандидатов, включая расширенные semantic.
`retrieval_eval.jsonl` — проверенная по исходным текстам финальная разметка:
10 `near_exact`, 25 `paraphrase`, 15 `semantic`; 61 разный relevant URL.
Все near_exact и paraphrase имеют один positive; 9 semantic имеют 2–5 positives,
остальные 6 остаются специфичными. Разметка основана только на содержимом корпуса;
результаты retrieval не служили источником relevant IDs.
Старый локальный `data/eval_queries_50.jsonl` с graded relevance не использован:
его происхождение не установлено и его формат отличается от нового benchmark.

Проверка выполнена агентом по непосредственно прочитанным полям корпуса;
независимый человек-рецензент пока не участвовал. `notes` содержит проверяемое
основание каждого positive. Это фиксированная авторская разметка, а не результат
LLM-as-a-judge или проверки выдач. При последующей человеческой экспертизе
правки gold следует делать явно, с объяснением в diff и новой версией baseline.

Подбор покрывает анимацию, документальное кино, комедии, мелодрамы, триллеры,
фантастику, хоррор, вестерн, семейные, социальные, спортивные и военные истории.
Представлены и известные, и менее очевидные фильмы из разных частей корпуса,
с разным настроением и длиной текста (352–831 символ индексируемого документа).
В paraphrase нет названий целевых фильмов и совпадений из пяти подряд слов
с их исходными `what/about/why`. Эта проверка дополняет смысловую сверку,
но сама по себе не доказывает качество перефразирования.

При сверке кандидатов в q027/q028/q032 удалены предположения о невидимом
барьере, снеге и точном расстоянии во времени. В q036 размечены два документа:
«Его дом» и «Паб “Старый дуб”», поскольку оба описывают семьи беженцев,
испытывающие трудности после переезда в Великобританию. Разные причины трудностей
и разные жанры допустимы для формулировки этого запроса. Тематического сходства
без подтверждения всех существенных условий запроса недостаточно для positive.

Расширение semantic выполнено по всем 500 сюжетным полям `about`, с просмотром
`what/why` у возможных positives и проверкой тематических упоминаний во всех
индексируемых текстах. В частности, произведения, перечисленные лишь как другие
работы режиссёра или актёров, не подтверждают сюжет самого документа.
`not_for` не использовалось для обоснования дополнительных IDs.

Для q039 сюжет должен описывать изменение жизни семьи из-за болезни или
наркотической зависимости. Наличие больного героя само по себе недостаточно.
Для q044 текст должен подтверждать и мистическую атмосферу, и затруднение выхода;
поэтому «Маяк» не добавлен на основании внешних знаний об изоляции.
Для q050 требуется изменение жизни принимающего сообщества; повествование только
о трудностях самого мигранта недостаточно. Запрос не требует явно описанной
ксенофобии, поскольку в индексируемых полях «Катцельмахера» она не утверждается.

```yaml
queries: 50
queries with 1 relevant document: 41
queries with 2+ relevant documents: 9
average relevant documents per query: 1.34
```

Это небольшая целевая выборка, а не случайная репрезентативная оценка всего
корпуса. Тип запроса задаёт способ формулировки и предполагаемую сложность;
он не гарантирует монотонное падение результата от near_exact к semantic.
В естественных semantic-запросах могут остаться явные жанровые и тематические
слова; BM25 способен находить их лучше, чем перефразированные сюжетные детали.
Recall измеряет найденную долю размеченных positives; релевантный, но не
размеченный фильм не засчитывается. Расширять positives можно только по корпусу,
без подгонки под выдачу конкретного backend.

## Проверка и обновление

```bash
uv run python -m movie_rag.evaluation --validate-only
```

Validator проверяет уникальный непустой `query_id`, непустой `query`, непустой
список `relevant_ids`, существование URLs в текущем корпусе, отсутствие повторов
в positives и один из трёх разрешённых типов. Ошибки JSON сообщают номер строки;
ошибки записи — также `query_id`. Изменение URL или удаление фильма требует
явного пересмотра разметки. Изменение индексируемого текста требует повторной
смысловой проверки: validator проверяет структуру и IDs, а не смысл.

Для нового корпуса можно получить независимые черновики:

```bash
uv run python -m movie_rag.evaluation.candidates \
  --output /tmp/retrieval_eval_drafts.jsonl --count 50
```

Генератор берёт документы по квантилям длины `about` и создаёт только грубые
`near_exact`-заготовки. Он не вызывает поиск, модель или LLM. Эти записи
помечены `UNREVIEWED`: нужно переписать запросы в нужное распределение,
проверить смысл и все подходящие документы, затем вручную перенести одобренные
записи в gold. Этот генератор не воспроизводит авторскую gold-разметку.
Он запрещает запись в стандартный gold и corpus и открывает output исключительно
для создания нового файла, защищая также существующие кандидаты.

## Метрика и результаты

`Recall@K = |set(relevant_ids) ∩ set(retrieved_ids[:K])| / |set(relevant_ids)|`.
Валидатор запрещает дубликаты relevant IDs; повторные retrieved IDs занимают
позиции, но считаются один раз. Overall и группы — невзвешенное среднее по
query (macro average). Пустая группа имеет `count=0` и score `null` / `n/a`.
Сбой backend прерывает запуск и не превращается в нулевой Recall.
У query с N positives максимальный Recall@1 равен 1/N даже при идеальном
первом результате. Поэтому оценку новой разметки нельзя сравнивать с оценкой
старой версии, где почти каждый запрос имел единственный target.

Runner вызывает `search(query, top_k=max(ks))` один раз на запрос. По умолчанию
результаты идентифицируются по `url`; `id_getter` позволяет адаптировать другие
форматы выдачи к тем же IDs. Изменение retrieval для запуска не требуется.
Проверка датасета происходит до загрузки модели.

Per-query JSONL содержит текст, тип, positives, ranking URLs и Recall@1/3/5/10/20.
Summary JSON содержит overall, группы, размеры выборок и параметры запуска:
backend, модель (для Dense/Hybrid), Hybrid candidate depth/RRF, SHA-256 gold
и индексируемых текстов с URLs. Для сравнения запусков проверяйте совпадение
хешей и `ks`. Артефакты записываются в `artifacts/eval/` и исключены из Git;
для разных backends задавайте отдельные output paths.
Статистика количества positives выводится также при `--validate-only`
и сохраняется в summary как `dataset_statistics`.
`--retriever reranker` оценивает существующий Hybrid + BGE reranker; summary
дополнительно фиксирует reranker model, число кандидатов, batch size,
максимальную длину пары и фактически выбранное устройство. `--candidate-k`
задаёт глубину обоих исходных поисков Hybrid и бюджет reranking. Если он меньше
`max(ks)`, существующий wrapper вернёт не более этого количества документов.

## Baseline на зафиксированном gold

[Сравнительный отчёт](../../reports/retrieval-benchmark-comparison.md) содержит
таблицы Recall@1/3/5/10/20 для overall и каждого типа запроса, а также разницы
между режимами в процентных пунктах.

Запуск 2026-10-02: 500 документов, BGE-M3 на CUDA, существующий кэш embeddings;
Hybrid `candidate_k=20`, `rrf_k=60`. Четвёртый режим использует существующий
`RerankedHybridRetriever` и `BAAI/bge-reranker-v2-m3`: 20 Hybrid-кандидатов,
batch size 4, max length 512, CUDA/FP16. Оценка повторена с выдачей top-20
и `ks=[1, 3, 5, 10, 20]`. Тексты, IDs, реализация и параметры
retrieval не изменены. Все четыре запуска используют один gold SHA-256:
`955e82dcc10e561b5c9749473408aad3078d0312b05197a164df38a5073c90e9`.

| Backend | Recall@1 | Recall@3 | Recall@5 | Recall@10 | Recall@20 |
| --- | ---: | ---: | ---: | ---: | ---: |
| BM25 | 0.352 | 0.432 | 0.516 | 0.590 | 0.620 |
| Dense | 0.581 | 0.733 | 0.800 | 0.865 | 0.932 |
| Hybrid | 0.586 | 0.712 | 0.801 | 0.872 | 0.922 |
| Hybrid + Reranker | 0.841 | 0.890 | 0.890 | 0.917 | 0.922 |

Recall@10 по типам запросов:

| Backend | near_exact (10) | paraphrase (25) | semantic (15) |
| --- | ---: | ---: | ---: |
| BM25 | 1.000 | 0.480 | 0.499 |
| Dense | 1.000 | 0.920 | 0.682 |
| Hybrid | 1.000 | 0.880 | 0.773 |
| Hybrid + Reranker | 1.000 | 0.960 | 0.790 |

Recall@20 по типам запросов:

| Backend | near_exact (10) | paraphrase (25) | semantic (15) |
| --- | ---: | ---: | ---: |
| BM25 | 1.000 | 0.520 | 0.532 |
| Dense | 1.000 | 0.960 | 0.840 |
| Hybrid | 1.000 | 0.960 | 0.807 |
| Hybrid + Reranker | 1.000 | 0.960 | 0.807 |

При K=20 Dense превосходит Hybrid на semantic. Recall@20 reranker совпадает
с Hybrid: он переставляет тот же набор из 20 кандидатов и не добавляет документы.

Полные значения всех пяти K по каждой группе сохранены в
`artifacts/eval/retrieval_summary.json`, `dense_summary.json`, `hybrid_summary.json`,
`reranker_summary.json`.
Соответствующие `*_results.jsonl` содержат по 50 per-query записей с ranking URLs
и дробным Recall для запросов с несколькими positives. Проверены одинаковые
хеши gold и корпуса во всех четырёх отчётах. В этой небольшой выборке Hybrid повышает
semantic Recall@10 относительно Dense, но Dense лучше на paraphrase;
overall не заменяет проверку этих различий.
Reranker улучшает overall Recall@1 с 0.586 до 0.841 и Recall@10 с 0.872 до 0.917;
на semantic рост Recall@10 скромнее: с 0.773 до 0.790. На paraphrase он находит
единственный positive первым для 24 из 25 запросов. Эти результаты относятся
к данной фиксированной выборке; оценка не меняла разметку под выдачу.
